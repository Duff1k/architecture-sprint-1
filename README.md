# Микрофронты на основе Single SPA
Для разделения на микрофронты я остановился на способе, о котором узнал на курсе - **single spa**.

## 1. Разделение на микрофронты

Чтобы разбить исходный монолит на микрофронты, в начале разделил на зоны бизнес-логики:

### 1.1. Работа с карточкой (cards-app)
- CRUD операции с карточкой, лайки (можно бы было вынести тоже в отдельный микрофронт, но мне кажется это избыточно).

### 1.2. Работа с профилем пользователя (user_info-app)
- Редактирование профиля (аватар, имя и т.д.).

### 1.3. Сервис авторизации/аутентификации (auth-app)

### 1.4. Хост для микрофронтендов (UIShell)
- Насколько я понял, single spa требует хоста, чтобы объединить наши микроинтерфейсы в одно приложение.

## 2. Структура каждого модуля

Предполагается, что каждая зона в микрофронте повторяет те же директории, что и в монолитном приложении:

- src/
- ├── blocks/
- ├── components/
- ├── images/
- ├── utils/
- └── vendor/


Только каждый файл в директориях был перенесен в соответствии с принадлежностью к конкретному микрофронту. За исключением `api.js`, где уже содержимое было разнесено в созданные `api.js` файлы каждого микрофронта.

> **Примечание:** Не уверен в правильности подхода с хостом, но показалось, что некое статичное содержимое тоже можно перенести туда, а не оставлять там только `index.js` с логикой редиректа.
